## UPLOAD+PRINT RECIPE (stock firmware — verified by A-to-PC/Kobra-3-Max-Journey, MIT)
Source: github.com/A-to-PC/Kobra-3-Max-Journey (Days 11-12, 17-18, 27-29)
+ chrisfore/anycubic_ha_local (handshake). Cached full text:
~/.hermes/cache/web/github.com-59d6f19802.md
1. GET http://<ip>:18910/info → JSON incl. `fileUploadurl` (pre-signed, ready to use)
2. POST multipart/form-data to fileUploadurl: text field `filename` + file under form
   field name **`gcode`** (NOT `file` — that exact bug cost the source author days;
   verified against real packet capture of Slicer Next)
3. Printer extracts package, 3MF precheck (fails on low space), finds plate_*.gcode
   (prefers Metadata/plate_1.gcode). .gcode.3mf = native package format
4. MQTT print/start on `.../slicer/printer/{model}/{device}/print` — payload MUST include
   task id, filename, md5 of uploaded file, file size, ams mapping (command without
   md5/filesize = unreliable)
GOTCHAS:
- "busy, cannot upload while printing" = real distinct rejection; check state first
- Touchscreen can stick on "Downloading files" after SUCCESSFUL upload — verify via
  MQTT file listing, never trust the screen state
- `; filament_colour_type` comment line CRASHES the Go firmware → PrintWatch STRIPS it
  on upload (documented safety feature — README selling point)
- Producer-string check exists in firmware (`; generated by AnycubicSlicer`); if third-
  party gcode gets rejected, prepend matching producer header line
- Verify upload endpoint on a real Kobra 3 V2 Thu (source tested a 3 Max; same family,
  anycubic_ha_local validated V2 monitoring)
v1 SCOPE: user sends pre-sliced file via Telegram → upload+print. Agent-side slicing
(OrcaSlicer CLI on Nexus) = stretch. Demo beat: send file → upload → print starts.

--slice 0 --outputdir ... --export-3mf. Server-side precedent: orca-auto project
(Ubuntu 24.04, headless via Xvfb, slice→Moonraker push). Nexus = Ubuntu 23.04+ ok.
